- **Repo-internal observations for the code-review phase (not alignment labels — no library documentation is contradicted).**
  - **(a) §7.3 "8 statuses × 9 actions".** The pure test matrix row lists nine names (`submit`, `accept`, `decline`, `cancel`, `ready`, `complete`, `noShow`, `expire`, `reuse`), but §6.1's transition table defines only **eight** wire actions and describes `reuse` as an *outcome*: "Repeating the **same** action when the order is already in its target state is a success with `reused: true`". The implementation exports eight wire actions and models the repeat as `{ kind: 'reused' }`; the test spells out all 64 wire cells independently of the resolver and asserts the idempotent-repeat policy separately ("reuses only the repeat of an action already applied", "pins the eight wire actions and keeps reuse out of the union"). The §7.3 row is covered in substance, but not as a literal nine-column table — worth a deliberate confirmation that §7.3's "9 actions" is documentation vocabulary rather than a ninth wire action.
  - **(b) Omitted `expectedSubtotal`.** See Recommendation 3. The §6.2.5 step-8 bullets cover "client sent a number", "client sent `null`", and "both null/undefined"; the omitted-value case is not specified, and the implementation resolves it conservatively (reject with `PRICE_CHANGED`).
  - **(c) The spec's effective-open snippet is out of date, not the code.** §6.5 writes `openStatusAt(business.hours, business.timezone, now)` (three arguments), while the real `convex/businesses/publicHours.ts` exports `openStatusAt(hours, clock)` (two arguments).
