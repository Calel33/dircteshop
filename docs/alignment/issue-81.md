**Top DRIFT findings:**

1. **Medium — new code still writes with the backwards-compatibility `ctx.db.patch(id, value)` overload** (rows 30–31: `orderThrottle.ts:228,232`, `orderBlocks.ts:174,248`, `orderThrottleCleanup.ts:40`, `devProof.ts:390,483,616`). The current API reference labels these 1-argument overloads "Supported for backwards compatibility. Prefer `db.patch(tableName, id, value)` in new code", and the project's Convex guideline states the table-first form. It works and is covered by tests, so nothing is broken; the cost is that #81 adds eight more call sites onto a form the library has already asked new code to stop using — and #82 already reported the same drift elsewhere in the repo. The delta is internally inconsistent (its `db.get('orders', id)` calls use the preferred form).
2. **Medium — the daily cleanup cron is pinned to the top of the hour** (row 32). `{ hourUTC: 4, minuteUTC: 0 }` is the exact shape the cron docs mark with ❌ ("Runs at the busiest moment of the hour") and which the `@convex-dev/no-top-of-hour-crons` lint rule flags; the `minuteUTC` JSDoc explicitly recommends omitting it so Convex spreads runs across the hour. A single daily job's blast radius is small, but the guidance is unambiguous and the cost of omitting `minuteUTC` is zero.
3. **Medium — the throttle is a hand-rolled counter the vendor recommends replacing with a component** (row 33). The Convex guideline says "For per-key quotas, cooldowns, or throttling, use `@convex-dev/rate-limiter`; hand-rolled counters and window scans race under concurrency and lose quota when a mutation fails". The delta attacks exactly that race (serialization write, read-both/judge-both/write-both, live OCC evidence), so the warning's concurrency half is answered on the record — but the recommended component also supplies `reset` (this ticket's `clearContactThrottle`), per-key windows and transactional rollback, and adopting it would delete a table, an index and a cleanup cron. Advisory: the protocol pins the table shape, so this is a product decision, not a bug.
4. **Low — the proof harness calls `ConvexHttpClient.mutation` with a raw string behind an unsafe cast** (row 34) where the documented `makeFunctionReference(name)` exists for code-generation-free clients; behaviour is identical, so this is a typing/idiom divergence confined to a dev-only script.

## Recommendations (advisory)

1. **(Medium) Finish the table-first write migration inside the new modules.** Change the new `ctx.db.patch(row._id, …)` / `ctx.db.delete(row._id)` calls to `ctx.db.patch('orderThrottle', row._id, …)` / `ctx.db.delete('orderBlocks', row._id)` and the same in `devProof.ts`. Mechanical, no behaviour change, and it removes the last inconsistency with `ctx.db.get('orders', id)` in the same files. The pre-existing sites in `orderThrottle.ts:96,119` can ride along or be left to a dedicated sweep (issue #77/#82 reported the same pattern).
2. **(Medium) Drop `minuteUTC` from the cleanup cron** — `crons.daily('cleanup stale order throttle', { hourUTC: 4 }, …)`. Update `convex/orderExpiry.test.ts:439-442` to assert the schedule without `minuteUTC` (or with whatever minute the platform reports). Zero-cost compliance with the documented anti-pattern guidance.
3. **(Medium, product) Record the rate-limiter decision.** Either (a) keep the hand-rolled table and add one sentence to `orderThrottle.ts`'s header saying the Convex guideline recommends `@convex-dev/rate-limiter`, that protocol §6.2.2 L1009 pins the `orderThrottle` shape instead, and that the OCC race is proven in `tasks/issue-81-concurrency-evidence.md`; or (b) evaluate the component for a later protocol revision (it would also retire `orderThrottleCleanup.ts` and the daily cron). ## Notes

- **Two documented recommendations are deliberately not followed, and both are recorded above rather than silently accepted.** The hand-rolled throttle (row 33) is mandated by the product protocol; the `crons.daily` choice (row 40) conflicts with the project's generated Convex guideline. Neither is a correctness defect, and the delta's own concurrency evidence answers the race the throttle guideline warns about.
- **Precedent, not a new class of finding.** `docs/alignment/issue-77.md` and `issue-82.md` already reported the 1-arg `ctx.db.patch` as a Medium DRIFT in `convex/businesses/mutations.ts`; rows 30–31 are the same drift re-appearing in new files. Treating them together as one remediation is cheaper than per-file fixes.
- **Spec conformance is out of scope here.** Whether the S4 abuse controls implement protocol §7.2 L1625–1637 (block blocks both channels, 3/10 min + 10/24 h, generic refusal, audited clear), whether the four §7.3 races are the right four, and whether the evidence record is sufficient are code-review inputs. Alignment only says the *technology usage* behind them matches current documentation.

The evidence file states this limitation itself (its "Limitations (explicit)" §1). Nothing here contradicts the docs; the docs simply do not describe the mechanism.
- **`skipQueue` is load-bearing and correctly used.** Without it, `ConvexHttpClient` serializes mutations per instance and scenario 1 would prove nothing. Both the class page ("Mutations are queued by default") and `HttpMutationOptions` state this, and the harness comments it at the call site.

Row 33 rests on it directly, rows 30–31 draw on it alongside the public API reference, and row 40 records where it contradicts the public docs.
