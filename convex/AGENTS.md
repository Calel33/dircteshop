# Convex

## Overview

The Convex backend for LocalConnect / LocalHub. It owns the database schema, all data mutations and queries, the listing approval state machine, authorization guards, Clerk webhook ingestion, and the idempotent seed scripts. The UI never touches the database directly; every read and write goes through the functions in this directory.

## Key files

| File | Owns |
|---|---|
| `schema.ts` | All tables and indexes (`users`, `categories`, `businesses`, `menuGroups`, `menuItems`, `serviceOfferings`, `stylists`, `orders`, `bookings`, `quoteRequests`, `auditLogs`, `notifications`) |
| `authz.ts` | `configuredSuperAdminIds`, `requireSuperAdmin`, `requireBusinessOwner` guards |
| `businesses/helpers.ts` | `resolveTransition` (state machine), `buildSearchText` |
| `businesses/ownerSavePolicy.ts` | core vs content field classes, save mode per status, moderation reason policy |
| `businesses/mutations.ts` | save + transition mutations, `authorizeAction`, patch allowlist |
| `businesses/queries.ts` | business queries incl. approved only projections |
| `businesses/seed.ts` | idempotent business seed |
| `categories.ts` | `listOrdered`, `bySlug`, `seedCategories` (internal mutation) |
| `users.ts` | `upsertFromClerk`, user lookups |
| `http.ts` | Clerk webhook route |
| `clerk-webhook-events-catalog.md` | webhook event reference |

## Commands

```bash
npx convex dev       # separate terminal, required for the database
npx convex run <fn>  # run a function from the CLI (seeds, e.g. categories:seedCategories)
npm test             # verify-state-machine.ts first, then node --test
npm run seed         # node scripts/seed.ts (type stripped, Node >= 22.6)
```

`convex/_generated/` is generated by the Convex CLI via `npx convex dev` / codegen. Never edit it by hand.

## Conventions

- The `convex/_generated/ai/guidelines.md` file (created with `npx convex ai-files install`) is the authority on Convex API usage; read it first when the task touches Convex code.
- Status transitions are driven by actions (`submitForReview | approve | requestChanges | reject | suspend | restore | reopenAsDraft`), resolved server side by `resolveTransition`. A client never passes a raw status and never patched a status field directly.
- `requireSuperAdmin` fails closed: identity, stamped `users.role`, and the live `SUPER_ADMIN_CLERK_IDS` env whitelist must all hold. The stamped row is a projection; the env whitelist is authoritative and is re-read on every request.
- `requireBusinessOwner` derives ownership from `businesses.ownerId`. Owner is not a `users.role` value.
- Owner saves respect `ownerSavePolicy`: fields are classed core or content. Core identity changes on an approved listing trigger re review; content edits go live immediately. Blank names and unchanged identity resubmits are rejected.
- `searchText` is maintained by mutations as `[name, keywords.join(' '), description].join(' ')`.
- Seeds are `internalMutation` so they are not client callable; run them via `npx convex run`.
- Anonymous visitor workflows (`orders`, `bookings`, `quoteRequests`) use token links, not Clerk accounts.

## Gotchas

- `bookings.startAt` is stored in UTC; render in the business's `timezone` (IANA name).
- `SUPER_ADMIN_CLERK_IDS`: exactly one ID in production, comma separated for local. Changes take effect on the next request, but existing users also need a Clerk user update (webhook) or a one time role backfill before `/admin` access.
- Owner deletion policy is still open (SPEC §3): deleting a Clerk user leaves `businesses.ownerId` dangling. Do not ship that path without a decision.
